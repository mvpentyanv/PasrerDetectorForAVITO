## 1. Введение

Авито постоянно обходят автоматические сборщики данных. Кто-то следит за ценами конкурентов, кто-то собирает сводки по категориям, кто-то выгружает контакты продавцов. Такой трафик нагружает инфраструктуру, портит продуктовую аналитику и превращает данные площадки и её пользователей в чужой товар.

Блокировать такие запросы по IP или user agent почти бесполезно: парсер меняет их за минуту, а если по ошибке заблокировать живого пользователя, это обходится дорого. Подделать поведение гораздо сложнее. Как быстро и ровно идут действия, как двигается курсор, как устроен обход выдачи: на этом я и строил решение.

## 2. Задача и цель

По условию задания нужна бинарная классификация на уровне `cookie_id`. `target = 1` означает трафик известных сервисов сбора данных (парсеры цен, сводок по категориям, контактов продавцов), `target = 0` означает человека. Для каждой куки из теста нужно выдать непрерывный score от 0 до 1: чем выше, тем вероятнее бот.

Помимо самой цифры, мне хотелось сделать работу, которую не стыдно показать:
- пройти полный цикл: EDA, поиск утечек, честная валидация, признаки, модели, анализ ошибок;
- получить модель, которую можно объяснить: какие именно особенности поведения выдают бота;
- прямо показать, где подход упирается в потолок, а не только итоговое число;
- сделать так, чтобы весь результат пересобирался одной командой.

Ограничения из условия задания, которых я придерживался:
- признаки строятся только по событиям куки внутри её суточного окна, без информации из будущего;
- `cookie_id` не используется как признак ни в каком виде;
- любые кодировки, зависящие от таргета, считаются только out-of-fold;
- никаких LLM больше 1B параметров и внешних API, всё работает локально и офлайн;
- фиксированные seed, точные версии библиотек, версия Python указана;
- на лидерборд всего 7 попыток, поэтому решения принимаются только по локальной валидации.

## 3. Данные и метрика

| Файл | Содержимое |
|---|---|
| `data/train.csv` | `cookie_id, cookie_created_at, window_start_ts, window_end_ts, target`, 11 091 кука |
| `data/test.csv` | то же без `target`, 4 909 кук |
| `data/events.csv.gz` | 328 905 событий: `cookie_id, event_ts, eid, event_name, platform, user_agent, item_id, item_category, item_location, seller_type, search_query, search_page, pointer_x, pointer_y` |

Типы событий: просмотр выдачи и объявления, листание фото, страница продавца, показ телефона, открытие чата, отправка сообщения, избранное, логин, показ капчи. Сами данные в репозиторий не входят. Вместе с ними в задании были `quickstart.ipynb` (пример загрузки и простой модели), `metric.py` (официальная реализация метрики) и `sample_submission.csv` (формат ответа), они лежат в корне.

Метрика: Precision при Recall >= 0.7. Среди всех порогов, при которых модель находит не меньше 70% ботов, берётся максимальный precision. Куки с одинаковым score образуют одну группу: при пороге отмечаются либо все, либо ни одной. Отсюда важное следствие: score должен быть непрерывным, жёсткие правила вида 0/1 здесь только вредят. Для диагностики я дополнительно смотрю PR-AUC и ROC-AUC.

## 4. Отчёт о работе

Шёл по этапам: окружение, EDA, метрика и валидация, baseline, признаки и бустинг, финализация. После каждого этапа фиксировал выводы и только потом двигался дальше.

### 4.1 Окружение и воспроизводимость

- Python 3.12.3, отдельный venv, точные версии библиотек в `requirements.txt`.
- Пути, seed (42), число фолдов и сиды для усреднения собраны в `src/config.py`.
- Загрузка и приведение типов в `src/data.py`: одна функция разбирает время во всех трёх файлах.

### 4.2 Разведочный анализ (EDA)

Весь анализ с графиками в `notebooks/eda.ipynb`. Главное:

1. Баланс. Ботов 899 из 11 091, то есть 8.1%, и доля стабильна по дням (6-9%). Константа даёт P@R >= 0.7 около 0.08.
2. Время. Окна длятся ровно сутки. Train покрывает 6-19 апреля, test 20-26 апреля, то есть тест строго позже. Время в UTC с точностью до секунды.
3. Утечка. События вне окна есть только у train-кук: у 77% ботов и 45% людей. Там же лежат все 7 928 показов капчи, и 88% из них приходятся на ботов. По сути это реакция антибот-системы, которая случилась уже после детекции. Без строгого фильтра по окну модель выучила бы признак, которого в тесте просто нет.
4. Дубли. Около 1.5% событий, доля одинаковая у обоих классов, так что это технический артефакт.
5. Пропуски структурные: зависят от типа события и платформы. Курсор, например, есть только на web.
6. Поле `platform`. 11 вариантов написания (web, WEB, Web, desktop и т.д.) случайно чередуются внутри одной куки и с таргетом не связаны.
7. Поле `user_agent`. 148 значений, все встречаются и в train, и в test. Даже среди явно автоматических (curl, Scrapy, HeadlessChrome) ботов всего 20-27%, так что жёстких "ярлыков" нет.
8. Поведение. Самый сильный одиночный сигнал даёт курсор (AUC около 0.94 по разбросу X). Дальше идут темп (медиана интервала 14 с у ботов и 47 с у людей), глубина листания выдачи, разнообразие городов и возраст куки.
9. Сдвиг train/test. Adversarial ROC-AUC 0.50, внутри train между ранними и поздними днями 0.49, KS не больше 0.05. Сдвига нет.

### 4.3 Обработка данных (`src/data.py`)

- Время. Все `*_ts` приводятся к `datetime64[UTC]` одной функцией. Парсинг одинаковый для train, test и events, после него проверяю, что не появилось NaT.
- Окно `[start, end)`. Окно идёт ровно с 00:00 до 00:00. 68 событий стоят ровно на `window_end_ts`, а это уже полночь следующих суток, поэтому правую границу исключаю. В quickstart её тоже исключают. До начала окна событий нет, после окна 40 711 (12.4%). Кук без событий в окне не бывает.
- Утечка из будущего. События вне окна есть только у train, среди них все `captcha_shown`. Строгий фильтр по окну её полностью убирает.
- Дубли. Полных дублей 4 863, из них 4 293 внутри окна. Доля около 1.5% и одинаковая у ботов и людей, значит это артефакт логирования. Дубли удаляю, а их число на куку считаю до удаления и оставляю признаком `n_dup_events`.
- Платформа. 11 написаний свожу к трём семействам: web, android, ios.
- Пропуски не заполняю. Для бустинга NaN означает "не применимо" (например, курсор на телефоне), и он умеет с этим работать. Доли пропусков там, где поле по смыслу должно быть, идут отдельными признаками.
- Категориальные признаки:
  - `user_agent` как строку не использую, чтобы модель не заучила конкретные значения. Вместо этого считаю frequency encoding по train+test (таргет не участвует, утечки нет) и разбираю строку на несколько простых полей: тип клиента (браузер, приложение, headless, скрипт), браузер, версия, ОС. Редких значений нет, у каждого основного UA минимум 40 кук;
  - низкокардинальные категории отдаю бустингам как есть: LightGBM работает с pandas category, CatBoost кодирует их через ordered target statistics, которые не смотрят в таргет текущей строки;
  - категории и города объявлений сворачиваю в агрегаты: число уникальных, энтропия, частота смен;
  - OOF target encoding в итоге не понадобился: после этих шагов высококардинальных категорий не осталось.
- Поле `eid` один в один соответствует `event_name`, отдельным признаком его не беру.

### 4.4 Метрика и схема валидации

Метрику (`src/metrics.py`) написал строго по определению:
1. уникальные score сортируются по убыванию;
2. TP и FP накапливаются целыми группами равных score;
3. берётся максимум precision среди порогов с recall >= 0.7.

Тесты в том же файле: игрушечный пример с ties, проверка, что группу равных score нельзя разрезать, проверка, что берётся максимум, а не первая подходящая точка, и сверка с официальной `metric.py` на 300 случайных наборах с ties. Совпадение точное.

Валидация (`src/validate.py`):
- Основная схема: StratifiedKFold(5, shuffle, seed=42). Считаю метрику по всем OOF-предсказаниям плюс среднее и std по фолдам. Модель передаётся функцией `fit_predict(X_tr, y_tr, X_va)`, поэтому всё, что зависит от таргета, физически видит только обучающую часть фолда.
- Почему основная схема не по времени, хотя тест лежит позже. EDA сдвига не показала: adversarial ROC-AUC 0.50, внутри train 0.49, KS не больше 0.05, доля ботов стабильна по дням. В такой ситуации стратифицированные фолды честнее: они используют всех 899 ботов и дают оценку разброса.
- Контроль: time-holdout. Учусь на окнах до 17 апреля, проверяю на 17-19 апреля (160 ботов). По смыслу это ближе всего к лидерборду, но слишком шумно, поэтому решений по holdout не принимаю.
- Шум. Std P@R >= 0.7 по фолдам около 0.05-0.06, разница между сидами около 0.005. Всё, что меньше примерно 0.01, считаю незначимым.
- Каждый эксперимент автоматически пишется в `reports/experiments.csv`.

### 4.5 Baseline-модели

- B0, пример из quickstart как есть: RandomForest на двух признаках (число событий и число уникальных объявлений). На его собственном сплите получилось 0.1025, в моей валидации 0.097. Разница от того, что я удаляю дубли.
- B1, логистическая регрессия на логарифме числа событий и долях типов событий: 0.171.

Уже на этом этапе было видно, что объём и состав событий почти ничего не дают. Нужны признаки поведения.

### 4.6 Признаки (`src/features.py`, 151 шт.)

Все признаки строятся только по событиям самой куки внутри её окна. Единственное исключение: частота user agent по датасету, это обычный frequency encoding без таргета. Train и test считаются одним и тем же кодом.

| Группа | Примеры | Чем бот отличается от человека |
|---|---|---|
| Курсор (web) | std, минимум, максимум X и Y, средний скачок, доля касаний края экрана, доля уникальных точек | У ботов "виртуальная" мышь: узкий разброс по X (std 203 против 553), смещена влево, часто упирается в края. Самая сильная группа |
| Темп | квантили интервалов, доля интервалов 2-20 с, энтропия интервалов, события в активную минуту, число сессий (разрыв больше 30 минут), доля ночной активности | Боты действуют чаще и ровнее: медиана интервала 14 с против 47 с |
| Темп внутри сессий | медиана, std и коэффициент вариации интервалов без длинных пауз, среднее, std и асимметрия логарифма интервалов | Паузы между заходами похожи у всех, а внутри захода бот быстрее и равномернее. Главный сигнал на мобильных, где нет курсора |
| Объявления и поиск | уникальные объявления, категории и города (всего и на событие), их энтропия, доля повторных просмотров, страницы выдачи (максимум, среднее, доля дальше первой, последовательное листание), запросов на выдачу | Парсер обходит каталог вширь: больше городов, глубже листает, почти не возвращается к уже открытому |
| Смены | доля соседних событий с другим городом или категорией | Обход без сценария, без "интереса" к чему-то конкретному |
| Типы событий | счётчики и доли 9 типов, отношения (контакты, фото, избранное, продавец на просмотр), 25 частых переходов между типами, энтропия типов | Больше просмотров объявлений и продавцов, меньше фото и избранного |
| Контакты | доля показов телефона у pro-продавцов, переход "страница продавца, потом телефон" | Сценарий выгрузки контактов |
| Устройство и кука | семейство платформы, поля UA, частота UA, смена UA, возраст куки | Куки ботов моложе (медиана 19 дней против 62), автоматические UA встречаются чаще |
| Пропуски и дубли | доли пропусков у полей объявления, `n_dup_events` | Слабые вспомогательные признаки |

Топ по среднему |SHAP|: `ptr_x_std`, `item_repeat_share`, `ptr_jump_mean`, `location_entropy`, `ptr_x_max`, `category_entropy`, `dt_q75`, `n_items_per_event`, `in_dt_cv`, `n_categories`. Полная таблица (gain, SHAP, permutation) в `reports/feature_importance.csv`, график в `reports/shap_summary.png`.

Набор признаков рос в две итерации. Первая версия, 140 признаков, покрывала все группы. Во второй (151) я добавил темп внутри сессий, частоту смен города и категории и признаки контактов. Это дало около +0.018 по среднему из трёх сидов.

| android | 285 | 0.37 | 0.65 | 0.52 |
| ios | 26 | 0.15 | 0.40 | 0.31 |

На мобильных нет курсора, это главная причина разрыва. К тому же у коротких мобильных кук (до 6 событий) информации почти нет, PR-AUC там 0.09-0.21. Но даже у мобильных кук, где событий больше 10, PR-AUC 0.71-0.74, а на web 0.76-0.94.

### 4.9 Что пробовал и что не сработало

- Популярность объявлений и запросов, то есть сколько разных кук их смотрели. Давала +0.06 (до 0.879): боты смотрят одни и те же объявления. От признака я отказался, потому что он строится по событиям других кук, в том числе из будущих дней, а это прямо запрещено условием. В реальной системе для такого признака ещё и нужна онлайн-агрегация по всему трафику.
- Optuna. 40 попыток, подбор на отдельном разбиении (seed 7), чтобы не подгонять параметры под фолды, по которым потом оцениваю. Прироста не дала (E10 против E7), оставил базовые параметры.
- CatBoost отдельно чуть слабее LightGBM, но в бленде даёт небольшую прибавку.
- Номер `item_id` распределён равномерно, сигнала нет.
- Отдельно пытался подтянуть мобильный трафик (web около 0.88, мобильные около 0.34 P@R и 0.625 PR-AUC). Каждый вариант проверял на LightGBM с 3-5 сидами, ни один не вышел за пределы шума ни по общему P@R >= 0.7, ни по PR-AUC на мобильных:
  - серии быстрых действий: самая длинная серия интервалов 3-20 с, максимум событий за 1, 5 и 15 минут, самая плотная сессия, автокорреляция интервалов. По отдельности AUC до 0.73, но всё это уже покрыто признаками темпа;
  - дополнительные поля UA: версия ОС и модель устройства (у M2101K6G 14% ботов);
  - согласованность внутри куки: совпадают ли категория и город открытого объявления с последней выдачей, доля главной категории (0.86 у ботов против 0.68), число городов на один запрос;
  - отдельная модель только для мобильных, без признаков курсора: на мобильных стало даже хуже (PR-AUC 0.613 против 0.624);
  - повышенный вес мобильных кук (x3) при обучении;
  - последовательность событий как текст: токены "тип события + корзина интервала", n-граммы 1-3, TF-IDF и логистическая регрессия, подмешанные в бустинг через вложенный OOF-стекинг. P@R на мобильных вырос с 0.34 до 0.37, но PR-AUC всего на 0.004, а общая метрика не выросла.

  Вывод: на признаках одной куки мобильный трафик близок к потолку. Сильный сигнал остался только межкуковый, а его условие задания не разрешает.
- Написание `platform` оказалось шумом, заменил его семейством.
- Доля дублей как признак слабая (AUC 0.55).
- Интервалы короче 0.3 с. Время в данных с точностью до секунды, поэтому "короче 0.3 с" на деле значит "0 с", и у ботов таких интервалов не больше, чем у людей.

### 4.10 Финальная модель

Ранговый бленд LightGBM (среднее по пяти сидам) и CatBoost на признаках v2, код в `src/train.py`. Выбрал его, потому что у него лучшие OOF P@R >= 0.7, PR-AUC и ROC-AUC. Разница с соседними вариантами в пределах шума, но смесь двух разных бустингов обычно устойчивее на новых данных.

Смешиваю именно ранги, а не вероятности: калибровка у двух моделей разная, и простое среднее вероятностей фактически дало бы одной из них больший вес. Итоговый score распределён по [0, 1] почти равномерно и калиброванной вероятностью не является, но метрике важен только порядок кук. Все 4 909 score в `submission.csv` уникальны: совпадения средних рангов я разбиваю крошечной добавкой вероятности (1e-6), которая не меняет порядок остальных кук.

Перед каждой отправкой файл проверяет `src/check_submission.py`: набор `cookie_id` совпадает с тестом, нет дублей и NaN, score в [0, 1], заголовок как в образце, нет больших групп одинаковых score.

## 5. Ограничения модели

- Зависимость от известных источников. Разметка сделана по известным сервисам сбора данных. Новый парсер с другим поведением, например с "человеческой" мышью и темпом, модель может пропустить.
- Шорткаты проверены. Без UA-признаков модель теряет всего 0.003-0.017, то есть опирается на поведение, и среди UA нет значений, где были бы только боты. Но главный сигнал на web это курсор, и бот с реалистичной эмуляцией мыши обойдёт эту часть модели.
- Мобильный трафик. Курсора нет, качество заметно ниже, чем на web, особенно на ios, где ботов совсем мало.
- Сдвиг. На этих данных его нет, но тест лежит позже по времени, и если парк ботов поменяется, качество может просесть. Стоит мониторить: adversarial validation, долю ботов, распределения ключевых признаков.
- Шумная метрика. При 180 ботах в фолде std около 0.06, так что результат на лидерборде может отличаться от OOF на несколько сотых в любую сторону.

## 6. Заключение

Что получилось:
- воспроизводимый пайплайн, который одной командой проходит путь от сырых событий до проверенного файла ответа;
- P@R >= 0.7 выросла с 0.097 (quickstart) и 0.171 (логистическая регрессия) до 0.823 у финального бленда, при ROC-AUC 0.947 и PR-AUC 0.808;
- модель объяснима. Бота выдают прежде всего неживой курсор, быстрый и ровный темп внутри сессии и обход выдачи вширь: много городов и категорий, глубокое листание, почти нет возвратов.

Главные решения и выводы:
1. Сначала данные, потом модель. Самая опасная находка EDA это утечка через события после окна наблюдения (капча и хвост активности). Они есть только в train, и без фильтра модель отлично выглядела бы на валидации и провалилась бы на тесте.
2. Честность важнее цифры. Популярность объявлений давала +0.06, но строилась на чужих и будущих событиях. Я от неё отказался и описал это открыто.
3. Метрика определяет решения. Из-за склейки равных score я реализовал метрику строго по определению, сверил с официальной и убрал ties из ответа.
4. Шум надо измерять. При std около 0.06 по фолдам многие "улучшения" оказались случайностью, поэтому решения я принимал по OOF на нескольких сидах, а не по одному прогону.
5. Отрицательный результат тоже результат. Шесть подходов к мобильному трафику прироста не дали, и это хорошо показывает, где проходит потолок поведенческих признаков одной куки.

Что можно сделать дальше:
- для мобильных нужны новые источники сигнала: телеметрия касаний и скролла, сетевые признаки или онлайн-агрегаты по объявлениям, которые считаются в реальном времени и не заглядывают в будущее;
- откалибровать score и выбрать рабочий порог под реальную цену ошибок: заблокировать человека или пропустить бота;
- мониторинг дрейфа признаков и доли ботов, регулярное переобучение на свежей разметке;
- сохранять обученные модели и сделать отдельный скрипт инференса, чтобы не переобучать всё ради новых данных.

## 7. Как запустить

Python 3.12.3, Linux (проверял в WSL2, Ubuntu 24.04). Данные положить в `data/`: `train.csv`, `test.csv`, `events.csv.gz`.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python main.py            # данные -> признаки -> CV -> submission.csv (~10 мин)
.venv/bin/python main.py --no-cv    # без CV, только submission.csv
.venv/bin/python -m src.check_submission         # проверка submission.csv
.venv/bin/python -m pytest src/metrics.py        # тесты метрики
.venv/bin/python -m src.experiments <stage>      # эксперименты: baselines | boosting | features_v2 | tune | importance
```

Воспроизводимость: seed 42 везде, для усреднения LightGBM сиды `[42, 1, 2, 3, 4]`, точные версии библиотек в `requirements.txt`, данные в `data/` не изменяются.

### Структура

```
data/                    исходные данные (не меняются, в репозиторий не входят)

src/data.py              загрузка, время в UTC, окно, дубли, платформа
src/features.py          признаки (один код для train и test)
src/metrics.py           P@R >= 0.7 и тесты
src/validate.py          CV, OOF, time-holdout, лог экспериментов
src/models.py            модели в формате fit_predict
src/experiments.py       эксперименты: baselines, бустинги, подбор, важность признаков
src/train.py             финальная модель и предсказание теста
src/check_submission.py  проверка submission.csv
main.py                  весь пайплайн одной командой
reports/                 таблица экспериментов, важность признаков, лог прогона
submission.csv           итоговый ответ
quickstart.ipynb, metric.py, sample_submission.csv   материалы из задания
```

### Библиотеки (open source)

- pandas 3.0.6, numpy 2.5.3, scipy 1.18.1: данные и статистики;
- scikit-learn 1.9.1: StratifiedKFold, LogisticRegression, RandomForest (baseline), метрики, permutation importance;

- Optuna 5.0.0: подбор гиперпараметров (TPE);

- matplotlib 3.11.2, Jupyter, nbconvert, ipykernel: EDA;
- pytest 9.1.1: тесты.

Подходы: frequency encoding, нативная обработка категориальных признаков (LightGBM, CatBoost ordered target statistics), adversarial validation, усреднение по сидам, ранговый бленд.

LLM и внешние API не используются, всё работает локально и офлайн.
